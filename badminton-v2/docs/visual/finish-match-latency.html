Finishing a match — where the 3–5 seconds went

The live board took 3–5 seconds to show the next game after tapping a winner, on good internet. It was never a caching problem: it was seven network round trips, one after another, four of which asked for something already in hand.

Why trip 3 was the sharpest waste

The next game was already on screen as data.next. The query asked the server for a value sitting in the component's own props.

Why trips 5–7 were waste

refresh() re-read the session row (unchanged), the match list (outcome already known) and all sixteen player profiles (static all evening) — every five seconds, on the tablet and every player's phone.

After — three trips, and the middle no longer looks broken

The new handleFinish 3 × RTT ≈ 1.5 s

Independent calls now overlap, the redundant reads are gone, and the profile fetch disappears entirely behind a 60-second cache.

The board advanced to the correct next game. On the gym's slower network the same three trips land around 1.5 s rather than 3–5 s.

The ceiling, and why it isn't zero

Trips 1 and 2 are genuine writes; the board cannot honestly change until the server has accepted them. Removing them means painting the next game before the write returns — an optimistic update — which also needs the three writes folded into one transaction, because otherwise two devices finishing two courts in the same second can both promote the same game and quietly leave a court empty. That is a larger change and is deliberately not done here.

Two places this trades a re-read for a local copy

Both savings work by trusting something the device already holds. Copies go stale, so each one has a rule for when to stop trusting it.

The profile cache expires after 60 seconds. Caching by player id means an id already known is never re-read — so a nickname or avatar edited mid-session would never appear, where previously the 5-second poll picked it up. A substituted player is a new id and is always fetched. The TTL restarts only on a full re-read, never on a partial top-up: otherwise a trickle of substitutions would keep pushing the window out and an edit could hide indefinitely.
The promote falls back to a read when the queue may be moving. data.next is the tablet's own copy, so reordering the queue on the admin phone and tapping Finish a moment later could promote the stale head. Two guards: if a reload is in flight (isReloading) the queue head is re-read from the server first, and the promote itself carries .eq('status','queued') so a match another device already took updates zero rows and is detected rather than being put on a second court.

One bug fixed on the way, visible to players

buildCourtSlots gave court N the match at queued[N-1], so court 1 previewed the head of the queue and court 2 previewed the one behind it. Promotion always takes the head and gives it to whichever court finishes, so court 2's preview named a game that could never land there next. Every court now previews the head, and the wording changed from “Next up” to “Next in queue” — a true statement about the queue instead of a false prediction about a court.
