What is happening now

The server is a free NANO box with 406 MB of RAM. The programs on it (Postgres and its 28 connections, the API, Realtime's connections, the metrics exporter) hold about 520 MB. What doesn't fit sits in swap, which is slow disk pretending to be memory. Swap held 230–370 MB all day on Nov 15. The data itself is tiny (24 MB). This is a memory problem, not a data or traffic problem. Details: prod-memory-explained.html.

  1. 1
    Most memory is in swap. Idle parts of each service are pushed to disk. That's harmless until something needs them back.
  2. 2
    The change poll keeps needing them. Realtime asks Postgres “anything new?” about 1.5× a second, all session long. The poll is 49% of all database time. Sooner or later it touches a swapped page and has to wait for the disk.
  3. 3
    One slow query becomes a queue. While it waits, other queries pile up behind it. Every table answered in ~5.5 s at once at 16:02. Postgres starts cancelling statements (statement_timeout), and Realtime logs “Too many database timeouts”.
  4. 4
    20 phones make it worse. Every phone sees the stall at the same moment. Each one refetches, reconnects and retries, so the box gets more work exactly when it can least handle it.
  5. 5
    A restart doesn't clear it. A restart drops swap only 368 → 230 MB, and it refills within about an hour. Restarting mid-session cuts everyone off, then all the phones reconnect at once to a cold server.

Nov 15 session (Manila time)

The fix: stop asking, start telling

Today

Postgres Changes

  • Asks continuously while anyone has the app open (≈1.5×/s).
  • Checks access for every change × every phone inside the database.
  • It keeps touching memory that is in swap, so it is the first query to stall.
Plan

Broadcast from the database

  • Silent when nothing changes, so there is no poll.
  • Access checked once, when a phone joins its topic.
  • Topics: session:<id> (games, results, roster, receipts) and user:<id> (notifications, stats, my registrations).
  • Phones keep the same refetch, 30 s safety poll and keep-last-good board.
What this will not fix: the swap itself. The box still has 406 MB of RAM for about 520 MB of programs. It removes about half the database work and the constant poll, so stalls should be rarer. If they continue, the remaining fix is a compute upgrade. Plan and steps: tasks/todo.md.
