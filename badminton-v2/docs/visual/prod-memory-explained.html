Why the prod server runs out of memory

Your data is tiny (24 MB). The server runs out anyway because of everything Supabase runs around your data. Measured on the prod dashboard, Nov 15 2026, 4:20 PM, just after the restart.

Correction: I said earlier “about 1.3 GB of software on a 400 MB box”. That was wrong. 1.3 GB is memory promised to programs, not memory they use (explained in section 3). What programs actually hold is about 520 MB, on a box with 406 MB of RAM. It is still too much, just not three times too much. I had also written “477 MB RAM” before; the dashboard's own figure is 406.5 MB.

1. What fits, and what doesn't

The box has 406 MB of RAM. Programs hold about 520 MB. The roughly 345 MB that doesn't fit in RAM goes to swap: a file on disk used as overflow memory, far slower than RAM.

Program memory in RAM (fast) File cache: recently read files, given back on demand Program memory pushed to disk (slow)
  • Why swap hurts: swapped memory is fine while nobody needs it. When a program does need it, it waits for the disk. On a busy night that is a query stalling for seconds, and then the queue behind it.
  • Why not use the cache space instead? Linux decides that itself. It keeps recently read files in RAM and pushes idle program memory out. We can't change that on Supabase.
  • A restart doesn't fix it. At 1:42 PM swap was 368 MB. The 2:17 restart brought it to 230 MB, and it was back to 314 MB by 3:46 PM.

2. What is running on it

Every Postgres connection is a separate program on the box with its own memory. These are the 28 Postgres processes running on prod tonight, read from pg_stat_activity:

11
PostgREST connections
The API your app calls for every read and write. It keeps a pool open even when idle.
7
Realtime connections
Live updates: connect 2, subscription manager 3, access checks 1, change stream 1.
7
Postgres's own workers
Writer, checkpointer, archiver, autovacuum, WAL writer, replication launcher, pg_cron.
3
Supabase services
Metrics exporter, management API, pg_net worker.

Also on the box: PgBouncer, the connection pooler (its logs show it starting there at the 4:12 PM restart). Not measured How many MB each one uses: the Free-plan dashboard shows only the total. Whether Auth and the API programs themselves run on this box is also unclear; the dashboard doesn't say.

3. The “1.3 GB” number, explained

Promised: 1.31 GB

“Memory commitment” is every allocation programs have asked for. Linux says yes to all of them and only hands out real memory when it is actually written. It works like restaurant reservations: 1,310 booked, ~520 actually turned up.

Per Supabase's docs, each new Postgres connection counts Postgres's 270 MB shared area again until it starts writing its own copy. 28 processes inflate the promise fast.

Actually used: ≈ 520 MB

175 MB in RAM plus 345 MB in swap. This is what makes queries wait. The promise limit is 1.4 GB, with a warning at 1.36 GB. Past the limit, Linux starts killing processes, and Postgres can crash outright. Nov 15 sat at 1.24–1.31 GB, close to that line, which is why the dashboard says “Severe”.

4. Why so much for a 24 MB database?

  • Fixed cost, not your data. Every Supabase project runs the same full stack: database, API, live updates, sign-in, monitoring. That costs the same whether the data is 24 MB or 24 GB.
  • Free = the smallest box. NANO has about 400 MB, roughly what the stack needs before your app does anything.
  • Connections are the part we influence. Each open connection is another program in memory. With Postgres Changes, Realtime keeps extra connections and a constant poll for live updates.

5. What can bring it down

  • Broadcast (built on DEV): removes the constant poll, about half the database work. Realtime's access-check and subscription-manager connections exist for Postgres Changes, so they may close too. Measure after rollout
  • Fewer API connections: PostgREST keeps 11 open. Whether the Free plan lets us shrink that pool is unclear; worth checking.
  • More RAM (paid compute upgrade): the only option that removes swap outright.
  • Not helping: restarting (swap refills within about an hour) and shrinking Postgres's cache (only 15.6 MB of it is used).
