Win, loss and draw —
where the label comes from

A match can hold more than one game, so a pair has only beaten the other if it took every one of them. Pick an outcome below to see the rule applied. The amber note marks what the All Games list used to do instead, until 2026-09-06.

01 — the table

One row per game, not per match

match_results stores a row for every game inside a match: winning_pair_index (1 or 2) and game_number. A normal match writes one row. A session with split_match_scoring on writes two, from submitSplitResult() — which is what makes 1‑1 possible at all.

02 — two readings

Both screens, one derivation

Both panels call the same helper, getMatchOutcome(). They differ only in what they draw with the answer — a chip about you, or a line about the match.

My Games

Counting means every one of the three states is reachable, and the draw is drawn as 1–1 rather than the word.

All Games

src/views/PlayerView.tsx → getMatchOutcome()

  1. Count the rows each pair won — —
  2. One pair took them all → that pair beat the other.
  3. One game each → tied with. Neither gilded, neither greyed.

Line in the results list

This is the case that used to break. The old getLegacyWinningPairIndex() read only the earliest row, so it named whoever took game 1 the winner and greyed out the other pair. Both pairs won a game; neither beat anyone.
03 — the gap

Where they part company

They no longer part company — this is the table as it now stands. The draw was the only row that ever disagreed, and it is the only outcome that needs more than one match_results row to exist, which is exactly why a function named getLegacy… never had to handle it.

Worth knowing: the leaderboards were never affected. They go through computeStatsFromResults(), which has always looped every row, so a 1‑1 credits each player one win and two games. The bug was display-only — the results list on the All Games tab, and nothing downstream of it.
