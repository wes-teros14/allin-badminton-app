Season reset — the two ways to build it

Both approaches give the same result to a player: the boards show the current season, last year is still reachable, and every profile gets a year card. They differ in one thing only — whether a row’s season is decided when the board is read (A) or when the row is written (B).

Today — where each board’s numbers come from

Partners · the four Awards season‑ready

Already computed from raw matches and match_results, joined to sessions, which carries the date. Nothing stands in the way of a season window.

matches → sessions!inner(id)  ← the embed is already there

Individual · Cheers the blocker

Read player_stats and player_cheer_stats — running totals kept by triggers, with no date column. A total cannot be sliced by year. These two are the entire problem.

player_stats(games_played, wins)  ← lifetime, undated
Why not simply zero those totals? Eligibility also reads them — sessions_attended, 3 for most boards and 4 for Individual. Zero the counters on 1 January and nobody qualifies for anything until the 4th session of the new year, so every board sits empty for about a month and Attendance Streak drops to 1 for everyone. Both A and B avoid this the same way: the counters stay lifetime and keep feeding the gate — only the ranked number becomes season‑scoped.

What each one costs you

 A — read‑time filterB — write‑time season column
Database migration None Add season to matches and cheers, plus a backfill
What changes Code only. Individual and Cheers switch from counters to raw rows; every board takes a date window. Code, schema, and session creation — the season has to be written correctly on create and on edit.
Cost per board load 545 matches and 6,177 cheers today. Partners already pulls the matches, so Individual shares that fetch; Cheers is the one new read. Same rows, but filtered server‑side by an indexed column — the smallest read of the two.
Can you view any year? Yes — any window, including ones you haven’t played yet Yes — any stamped season
Fixing a result later Just works. The board recomputes. Works, as long as the row’s season was right to begin with.
Main risk Depends on Neon’s Data API filtering an embedded table the way PostgREST does. Unverified. A row with the wrong season is invisible and silent. Needs care on session edit.
Season boundary A date. Change your mind, change the constant. Baked into rows. Moving the boundary means a re‑backfill.

The check that decides it

A is the lighter build and the one that can never lose data, but it rests on a single unverified assumption. Ten minutes against Neon dev settles it:

matches.select('…, sessions!inner(date)').gte('sessions.date', '2027-01-01')
If that filters correctly — build A, with no migration at all.
If it doesn’t — fall back to B, and the season column earns its migration.

What players actually see, either way

On the leaderboard

A year switcher above the existing tabs. It opens on the current season, so the first night of the new year genuinely starts from nothing — but the boards are never empty, because who qualifies still comes from lifetime attendance.

On My Profile

A “Your 2026” card, sitting with the Cheered‑for and Awards cards. Games, win rate, best partner, signature cheer, any award held at year end — computed live, never a frozen copy.

Measured on production, 19 November 2026: 41 sessions since 22 March, 545 completed matches, 6,177 cheers. Source of the board logic: src/lib/leaderboardData.ts, src/lib/boardEligibility.ts.
