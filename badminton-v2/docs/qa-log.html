Routing & role gating

Which route is the admin page for one session, and who can reach it?

/session/:sessionId → SessionView. It is not the same route as the player-facing /sessions/:sessionId (SessionPlayerDetailView) — note the singular vs plural. All the admin routes sit behind AdminRoute in src/App.tsx:10, which reads role from AuthContext and redirects to / unless the role is admin or moderator.

So any admin shortcut placed on a player screen only needs to check the same two roles — the route itself is already protected, and the check is just there to avoid showing a dead-end button to players.

Accounts & profiles

I logged in with another email and the session page says "No schedule found for your account" — there's no Register button. Why?

That account had a login but no profiles row. A login lives in auth.users; the player record is a separate row in profiles, and the My Games tab (which holds the Register button) only renders when it finds that row's name_slug (SessionPlayerDetailView.tsx). Measured on prod 2026-10-04: mwca8888@gmail.com had an auth.users row from 2026-05-14, profile_id NULL, 0 registrations.

The on_auth_user_created trigger is supposed to create the profile at sign-up. The only client-side fallback (ensureProfile) ran on the invite-link page alone, so a player who signed in from Home had nothing to repair them. Branch 012-ensure-profile-on-login moves the fallback into AuthContext so every login creates a missing profile. Why the trigger skipped this account is still unconfirmed — run the pg_trigger check on prod.

I registered, so why am I not on the Players tab?

Same cause. The Players tab lists rows from profiles (usePlayers.ts), not login accounts, so a login with no profile row is invisible there while still being able to sign in. "Registered" in that case meant the account sign-up, not a session — the session_registrations count was 0. Note that a session registration does not prove a profile exists either: session_registrations.player_id references auth.users, not profiles.

Session cards

Why can’t an admin button just be dropped inside a session card on /sessions?

Because the entire card is one anchor. SessionRow in src/views/MySessionsView.tsx:126 returns a single <Link to={`/sessions/${s.id}`}> wrapping every line of card content, and HTML does not allow an anchor inside an anchor — React will render it, but the nested link’s behaviour and keyboard focus order are undefined.

Two legal ways out: make the admin control a <button> that calls navigate('/session/' + s.id) and calls stopPropagation() so the click never reaches the card, or lift it out of the link entirely — wrap the card in a relative container and absolutely position the admin control as a sibling of the <Link>. The second is cleaner: no event plumbing, and the tab order comes out right on its own.

Which sessions actually appear on /sessions, and does the admin shortcut cover all of them?

usePlayerSessions returns two groups merged together: every session you hold a registration for, in any status, plus every session whose status is registration_open or registration_closed whether you are registered or not. Nothing else.

So the admin shortcut reaches a session in setup, schedule_locked, in_progress or complete only if you are registered in it. A brand-new session sitting in setup that you haven’t registered for will not show on /sessions at all — that one still needs /admin.

Why does the header row of a session card have a negative right margin?

The admin shortcut is absolutely positioned in the card’s bottom-right corner, so the card carries pr-16 instead of pr-4 to keep long venue and note text from running underneath it. But container padding is charged to every row, and the top row’s status pills are shrink-0 flex-nowrap — so all 48 px came out of the session name and titles started wrapping to two lines for admins only.

The header row gets -mr-12 when isAdmin, which exactly cancels the difference. The name and pills keep the width they have with no shortcut, and every row below the header keeps the gutter the button needs.

Why does the badge row limit what can go in the top-right of a card?

The list is rendered inside max-w-sm (384 px) and the badge row already holds up to two pills — the status badge plus a separate “Registered” pill for in_progress, schedule_locked and registration_closed sessions. With a long status label like “Registration Open” and a long session name, that row is already near its width limit, so a third control there squeezes or wraps on a phone.

Correction

“Only your own court shows on /sessions/<id> because that tab is your personal schedule.”

Half right, and the wrong conclusion. The Schedule tab is per-player, and the court chip on your own card does follow your game — but that was never the whole story. The page had no court overview at all. A player mid-game saw one court because their own card carried a chip; a player between games saw none. Reported as “I finished my game and still see no Court 1”, which is what proved it.

Not a data problem: court_count was 2 and both courts were occupied. The two-court strip (PlayerCourtTabs + useCourtState) only ever existed in PlayerView.tsx, serving /match-schedule/session/<id>. When session cards started linking to /sessions/<id> instead, players silently lost the overview the admin view kept.

Fixed by extracting PlayerCourtTabs to src/components/ and rendering it on both routes. It shows every court whether or not you are on one.

Can we make the session notes adjust when it’s long? I don’t like it like this.

The note was rendered as one sentence under a line-clamp-2, so anything past two lines was cut mid-word — “…@ 1st 20 games….”. The fix was to stop treating it as a sentence at all: session notes are written as a pipe-separated list (6 games | 21 pts/game | 1 set/game | 1 new shuttle/game @ 1st 20 games), which is structured data wearing a sentence’s clothes.

splitSessionNotes() in src/views/MySessionsView.tsx splits on |, trims and drops empties, and returns null when fewer than two rules survive. Two or more rules render as wrapping chips (bg-muted, text-xs) and nothing is ever truncated — the block just grows a row. One rule, or a note written as prose, falls back to the old icon-plus-text line, now unclamped. Contrast holds in both themes: #6B5F73 on #F1ECF6 is 5.03:1 light, #B39DBB on #1E1230 is 7.14:1 dark.

Three alternatives were mocked and rejected: dropping the clamp alone (card heights go uneven and one chatty note dominates the scroll), a “Show more” toggle (the card is a single <a>, so the toggle has to live outside it — see the admin-button entry above), and demoting the note to one dim truncated line.

Leaderboard

Why is it hard to see each rank on the Partners board?

Five things stack up, and the first is a real layout defect rather than a styling preference: the rank column doesn’t line up. An untied place renders the rank inside the bordered card, after its px-4 (LeaderboardView.tsx:327); a tied place renders it outside, to the left of the cards (:337-345). So ranks sit about 16 px apart horizontally on the same board and the cards themselves start at two different x-positions — there is no column to run your eye down.

The rest: rank is drawn in text-muted-foreground while the win rate gets text-primary and bold, so the value that establishes ordering is the quietest thing on the row; RANK_ICON returns 🥇🥈🥉 then bare digits, and colour emoji beside a grey glyph share no weight, size or baseline, so places 4–10 read as absent rather than lower; the cell is text-sm w-5 — 14 px in 20 px — with no tabular-nums, so “10” and “4” don’t centre alike; and a tie group’s single rank glyph is top-aligned beside a 2 px rule with nothing stating how many are tied.

None of this is a data problem. rankPairs and groupByRank compute dense ranks correctly and cut on places rather than rows — the numbers are right, only the drawing is wrong.

Why do the top three places get a different treatment from places 4 and below?

Deliberate, and it needs the divider to stay legible. The medals are worth keeping where they mean something, but mixing them with plain digits in one continuous list is what made the lower places disappear. So places 1–3 became a podium — medal, ordinal label, tinted border — and every place below is one consistent 34 px numbered chip, with a “Places 4–10” heading between them so the change of visual language reads as intentional.

A tied place keeps the same 34 px chip as every other row and states “3 tied” in words above its rows; only the card grows. Keeping the chip width fixed is the point — it is what stops the original misalignment coming back.

Correction

“Mga Lodi ranks players 1, 2, 3 down the list.”

It did, and that was wrong. fetchAllTimeLeaderboard numbered rows by array index and cut with .slice(0, 10) — ten rows, not ten places. So two players both reading 67% would have been shown as separate places, and once the medal podium landed, one of them would have taken 🥈 purely for sorting later. The partnership board had never worked that way; only this one did.

Both boards now share src/lib/denseRank.ts: equal rates take the same place, the next distinct rate takes the next number (1, 1, 2 — not 1, 1, 3), and the cut counts places, not rows, so a board can show twelve rows across ten places. Sorting also gained a final tiebreak on player id, so the order no longer depends on what order Supabase returned the rows in.

Why does a partnership need both players to have 3+ sessions played?

Because “3 games together” alone was cheap to reach. A regular who plays every week could partner a first-timer for three games, win two, and put a 67% pairing into the top ten built almost entirely from one player’s form. The individual board had always required 3 sessions attended; the partnership board required only recent activity — one registration in the last four completed sessions.

Both boards now read the floor from the same player_stats.sessions_attended column via one MIN_SESSIONS_PLAYED constant, and rankPairs applies its eligibility predicate to both partners — so a pairing needs two qualifying players, not one. Recorded as FR-014a in specs/006-pair-winrate-leaderboard/spec.md.

Why were “Most Cheers Received” and “Most Cheers Given” removed?

Because both were attendance counts wearing a rosette. Cheering is not optional: PlayerLayout.tsx:28 replaces the entire page with the cheer gate while any cheer is pending, and the panel walks you through all three other players in the match — you choose only which type, never whether or whom. The Skip button writes to local React state, so a refresh brings the gate straight back; you cannot durably skip.

So cheers_given is three per match you played, and cheers_received is the same number, because the three others in each of your matches are each gated into cheering you. The two boards ranked the same thing, and the Awards tab’s 📅 Most Sessions Joined already ranked it a third time — honestly. The only variance between them was lag: a player who hadn’t opened the app yet hadn’t paid the cheers they owed. That is noise, not merit.

Why are the six cheer categories scored as a percentage now?

Because the raw counts had the same disease in milder form. The cheer type is the one genuine choice in the flow, so the categories carry real signal — but as counts they still largely ranked whoever played most: 20 matches yields 60 cheers spread over six categories, 6 matches yields 18. Removing the two totals and stopping there would have left two obvious attendance boards replaced by six subtle ones.

Each board now shows what share of that player’s own received cheers were of this type — “12 of 30 · 40%”. This works arithmetically because the trigger in migration 036 increments cheers_received and exactly one category by 1 per row, so a player’s six shares sum to 100%. A floor of MIN_CHEERS_RECEIVED (15, roughly one session’s worth) keeps a 4-of-4 sample from reading as a perfect 100% and taking the board — the same minimum-sample idea as min 3 games together on the Partners board.

Concretely: a player with 24 Offense cheers out of 120 total (20%) now ranks below one with 12 out of 30 (40%). Under the old count ranking the first won by double.

How can Jerome be top on Swift Movement with only 6 of 59 (10%)? Out of 59 cheers he didn’t get more than 10% of anything?

He did — the board just isn’t asking that. A cheer board asks “who, out of every eligible player, gives the biggest slice of their own cheers to this type”, not “what is this player best at”. rankCheerShares in src/lib/cheerShare.ts sorts by categoryCount ÷ totalReceived across players, and the winner is whoever has the highest share, however small that share is in absolute terms.

Measured on prod (2026-09-20): Swift Movement is simply the rarest cheer anyone gives. The whole podium is Jerome 10% (6 of 59), Luis 9% (3 of 32), Bon and Kurt 8%. Jerome’s own strongest types are elsewhere — Fierce Offense 37% (22 of 59, 2nd on that board) and Smooth Technique 24% (14 of 59, tied 4th). The remaining 17 cheers are spread across Defense, Good Sport and Effort. Compare Fierce Offense, where the gold sits at 45%: the gold means “highest share”, not “high share”.

The code was audited end-to-end for this question (eligibility → fetch → share → dense rank → cut to 5 places) and is doing what it was designed to do. The open question is a UX one: a gold medal for 10% reads as odd, which is a caption/threshold design choice, not a bug.

Where does “3+ sessions played and active in the last 4” actually live now?

In one place: fetchEligiblePlayerIds() in src/lib/boardEligibility.ts, which also owns MIN_SESSIONS_PLAYED, RECENT_SESSIONS_WINDOW and the excluded-account list. Every surface asks that one function — Mga Lodi, Partners, Cheers, Awards, and the award badges on My Profile.

It had been reimplemented inline four times, and the copies had drifted: the Cheers tab applied neither rule, so a player who had turned up twice a year ago could still hold a cheer board. The two exclusion sets were also duplicated under different names (CHEER_EXCLUDED and STREAK_EXCLUDED) holding identical ids.

Why does the Cheers tab show one cheer type at a time instead of all six?

Six boards stacked meant up to eighteen medals on one screen, six of them gold. A medal that appears six times per scroll stops meaning “best” and becomes decoration — the podium was designed for one board of ten places. The page also measured 3,920 px at phone width with only three qualifying players; a full club would have pushed it past 6,000.

A six-way switcher now shows one category at a time. Same fixture, the tab measures 1,600 px — and exactly one gold medal exists at any moment. The buttons are 54 × 51 px, above the 44 px touch minimum, and carry an aria-label with the full category name since the visible label is abbreviated (“Tech”, “Sport”).

What is the “Cheered for” card on My Profile, and why did the old Cheers cards go?

It answers the question the six category boards never could: what am I known for? One card showing your strongest cheer type, the share it represents, and a bar splitting your received cheers across all six. The segments add to 100% by construction — migration 036’s trigger increments cheers_received and exactly one category per row.

The old Cheers section below Stats showed the same six percentages again as seven stat cards, so it was removed and its total folded into the new card as “of 30 cheers received”. The exact per-category counts (“12 of 30”) are gone from the profile; they still appear on the leaderboard rows, and the denominator is what made the percentage trustworthy.

Why do the profile’s award badges compute their own ranking instead of reading the Awards tab?

They still compute it locally — the two views load independently — but they now run the same functions: fetchEligiblePlayerIds and rankCheerShares with maxPlaces: 1, resolving a tie to nobody exactly as the Awards tab does.

This matters because the two had silently diverged. After the Awards tab moved to shares, the profile was still awarding 🌟 Most Cheers Received and 🙌 Most Cheers Given and still ranking the six categories by raw count — so a player could see a badge on their profile that did not exist on the leaderboard, with no way to work out why. If you change one ranking rule, check both files.

Theming & light mode

We need a dark/light toggle and a real light mode. What actually has to change?

Three things, in order. index.html hard-codes <html class="dark">, so step one is a state holder that sets or clears that class. Step two is the light token block: the :root section of src/index.css exists but has never rendered — it is shadcn's stock light default with --primary: #6F3E87 dropped in. Step three is the control itself, which is the smallest part.

Design options are laid out in docs/visual/theme-toggle-options.html — a nav orb, a shuttlecock switch, and a Light/Auto/Dark segment. Each one is live in that file and repaints the whole page, so the proposed light palette can be judged rather than imagined.

Why can't we just flip the class and use the light tokens that are already there?

Four of them break. The worst is --muted, which changes role between the two blocks: light defines it as #6B7280, a mid-grey text colour, while dark defines it as #1E1230, a surface. Every bg-muted in the app turns into a grey slab the first time the light block is used. That is a bug, not a preference.

The other three are contrast failures on white: --gold #FFB200 measures 1.81 : 1 (the podium's first place would disappear), --destructive #DC595E 3.71 : 1, and --success #22C55E roughly 2.2 : 1 — all under the 4.5 : 1 floor. The fix is light-only overrides — #8A5A00 (5.94 : 1) as a new --gold-ink for gold text while #FFB200 stays the medal fill, plus #B3252B (6.55 : 1) and #157F3D (5.09 : 1). Dark-mode values stay as they are.

--primary #6F3E87 needs nothing: 7.69 : 1 against white and 7.69 : 1 against its own white foreground. It is the one token that carries across both themes unchanged, which is why the app still looks like itself in light mode.

Why does the toggle design bother with a third “Auto” state?

Because a two-state switch cannot say “match my phone”, and iOS and Android already schedule that at sunset. A plain on/off switch silently overrides the OS preference the first time it is touched. The trade-off is that three states means three things to persist and test instead of two, and it needs a full settings row rather than a 44 px nav slot — which is exactly why the three variants in the specimen sheet sit in different places in the app.

Correction

“The theme toggle can go in the hamburger menu, or next to it.”

Half wrong, and the wrong half matters. Both the hamburger button and the dropdown it opens are wrapped in hasAdminTabs in src/components/TopNavBar.tsx, which is role === 'admin' || role === 'moderator'. A plain player never sees a menu button at all — so a toggle placed inside that menu would be invisible to almost everyone who uses the app.

Where exactly would the toggle sit in the app?

Two slots. Nav bar — src/components/TopNavBar.tsx:145, between the tab list and the hamburger; visible on every screen for every user, but only 44 px wide so only an icon button fits. My Profile — src/views/ProfileView.tsx:405, a new Appearance row directly above the existing Sign out button, which is full width and fits anything, including a Light/Auto/Dark segment.

Whichever is chosen, the state itself has to live above <Routes> in src/App.tsx, not inside PlayerLayout — /live-board, /live-board/:sessionId and /register never mount that layout, so a layout-scoped provider would leave them on whatever class the previous page left behind.

Does the purple nav bar need a light version?

No. TopNavBar is bg-primary text-primary-foreground, and --primary is #6F3E87 in both token blocks — so the bar looks identical in either theme and needs no work.

The catch is that anything drawn on it must use currentColor, not var(--foreground). In light mode --foreground becomes #1B1220, which measures 2.37 : 1 against that purple — well under the 4.5 : 1 floor and effectively invisible.

Correction

“--gold is unreadable on white at 1.8 : 1 — the podium’s first-place text would vanish.”

The number is right, the reason was wrong. --gold is never used as text anywhere in the app: the podium applies it as border-gold bg-gold/[0.07] (src/views/LeaderboardView.tsx:98) and the award toast uses it as a border. So the rule that applies is the 3 : 1 floor for non-text UI boundaries, not the 4.5 : 1 text floor — and #FFB200 at 1.81 : 1 fails that too, so the fix is the same either way: light mode uses #B87A00 (3.61 : 1), dark keeps #FFB200.

Worth keeping because the wrong reason would have led to the wrong fix — a separate --gold-ink token for text that nothing would ever have used.

What was actually the dangerous part of turning light mode on?

--muted. The light block defined it as #6B7280, a mid-grey text colour; the dark block defined it as #1E1230, a surface. The app only ever uses it as a surface — bg-muted appears 106 times and bare text-muted zero times, since every muted text is text-muted-foreground. Switching to light would have turned every skeleton loader, hover state and table header into a grey slab. It is now #F1ECF6.

The same class of bug bit a second place: .live-board-dark overrides some tokens but uses text-muted-foreground without defining --muted-foreground. That worked only because <html> was always dark. The scoped block now carries its own. The general rule: a token defined in one theme block but not the other silently resolves to the wrong theme’s value.

Why doesn’t the app follow my phone’s dark mode automatically?

Deliberate. Dark is the default and only an explicit light in localStorage['badminton-theme'] switches it, so every existing player sees exactly what they saw before until they choose otherwise. Following the OS would have silently changed the app’s appearance for everyone whose phone is in light mode.

That default is also why the toggle is a two-state orb rather than a Light/Auto/Dark segment — there is no “Auto” to represent. Adding one later means swapping the control in the same Appearance row; the state lives in ThemeContext, not in the button.

Why is the theme provider in App.tsx and not in PlayerLayout?

Three routes never mount PlayerLayout: /live-board, /live-board/:sessionId and /register (src/App.tsx:59–61). A layout-scoped provider would leave those on whatever class the previous page happened to set. ThemeProvider wraps <Routes> instead.

There is also an inline script in index.html that applies the class before React loads. Without it a light-mode player gets a dark flash on every page load. It duplicates the rule in readStoredTheme() on purpose — change one, change the other.

Correction

“Only four tokens break when light mode is switched on.”

Wrong, and it shipped a visible bug: the award badges on /profile were unreadable in light mode. Four tokens broke, but I had audited only the tokens. Thirteen colours were written as hardcoded hex directly in className, where no token could reach them.

The audit swept for text-white, bg-white, text-black and bg-black. That pattern cannot match a Tailwind arbitrary value like text-[#FEFE6A], so the entire class was invisible to it. The sweep that finds them is grep -rEo "(text|bg|border|fill|stroke|ring)-\[#[0-9A-Fa-f]{3,8}\]".

#FEFE6A is the live board’s neon yellow and measures 1.01 : 1 on the light page. The six text-[#FFB200] spots in PlayerView, CourtCard, CourtTabs and MySessionsView measure 1.79 : 1 and would have been the next bug reports.

Why are there two gold tokens now instead of one?

Because in light mode one hex cannot do both jobs. As a medal border, gold needs 3 : 1; as lettering it needs 4.5 : 1. A gold dark enough to read as text (#8A5A00, 5.58 : 1) is darker than the amber-700 bronze sitting below it on the podium, which looks plainly wrong.

So --gold stays the medal, border and wash colour (#FFB200 dark, #B87A00 light) and --gold-ink is its text pair (#FFB200 dark, #8A5A00 light). In dark mode #FFB200 clears both floors on #1A1025 at 10.8 : 1, so the two are the same value and the split costs nothing. Rule of thumb: text-gold-ink for gold lettering, gold for everything else.

One visible side effect: the award badge in dark mode moved from the live board’s neon #FEFE6A to the app’s gold #FFB200, so it now matches the award toast and the podium’s first place instead of being a third yellow.

Why did the measured contrast numbers come out wrong twice?

Because getComputedStyle(el).color returns oklch(...) in current Chromium, and the check parsed it with a digit regex — so oklch(0.828 0.189 84.429) was read as the RGB triple (0.828, 0.189, 84.429), producing confident nonsense like “amber-400 is 18.56 : 1 on white”. It is 1.72 : 1.

The fix is to let the browser convert: paint the computed value into a 1 x 1 <canvas> and read getImageData. Worth remembering for any future contrast checking in this repo.

Match schedule

What is wrong with the All Matches schedule as it stands?

AllMatchesView (src/views/PlayerView.tsx:293) renders twenty identical cards. Five things follow from that:

1. It never says which court. The court strip lives on the other schedule view (ScheduleView), so the first question a player has — where do I go — is unanswered. 2. Nothing is anchored. Live, done and twelve-games-away all render at the same size, so finding “what is next” means reading every card. 3. Played games keep full-size cards at opacity-50. After fifteen games three quarters of the scroll is dimmed history, and 50 % opacity on body text drops it under the AA contrast floor. 4. Results are thrown away. A ✓ says “finished” but not who won, even though match_results.winning_pair_index is already there. 5. The vs divider costs a whole line per card and says the same word twenty times, while the two pairs — the part that differs — are drawn identically.

Correction of a correction

“The ← My Matches link is broken — it points at the route it is already on.”

That was my claim, and it was wrong. Mark caught it. The link does work, by a route I had not read: /match-schedule/session/:sessionId renders PlayerListViewInner, which auto-redirects a signed-in player who is registered for that session to /match-schedule/session/:id/:nameSlug with replace: true (src/views/PlayerView.tsx:216). So the link round-trips through the picker and lands on your own schedule.

How I got it wrong: I read the route table in App.tsx, saw that the target route had no :nameSlug, and concluded it could not reach a player’s schedule. Routes tell you what renders; they do not tell you what that component does on mount. The lesson is to follow the component, not just the URL.

What is actually true: the redirect needs three things — signed in, a name_slug on the profile, and a session_registrations row for that session. An admin who is not registered falls through to the “Select a player” picker instead. That is reasonable behaviour, not a bug; the label just reads oddly for that one case.

Why can’t the schedule just group games by court?

Because a court is only assigned when the admin sends a game on. useAdminSession returns courts, queued and finished as three separate buckets, and everything in queued has no court yet. With two courts running, only two of twenty games know where they are being played at any moment — a court-grouped layout would put eighteen games in an “unassigned” column.

That is why the three proposals sort by state, by order, or by person instead. It is also why any “Court” label on a queued game has to read something honest like “first open court” rather than a number.

Is the All Matches page the same UI a player sees by default?

No — they are two different components. The default landing page is ScheduleView at /match-schedule/session/:id/:nameSlug: your games only, drawn with GameCard, plus a PlayerCourtTabs strip and a “it’s your turn” banner. AllMatchesView is what you reach with ?show=all and shows all twenty. Redesigning All Matches does not change the default view.

What does the schedule page show when the session isn’t live?

Nothing, for two whole statuses. While the session is registration_open or registration_closed, no matches have been generated, so usePlayerSchedule returns an empty array, the list maps over nothing, and the player gets a header followed by blank space. There is no empty state in either component.

schedule_locked renders the full list with every game queued — no live card, no elapsed timer, and the “first open court” label would be wrong because no court is running. complete renders every row at opacity-50. The court strip is hidden only for registration_open (src/views/PlayerView.tsx:500), so registration_closed shows an empty strip above the blank space.

Why doesn’t the schedule page mention payment?

Because payment lives entirely on SessionPlayerDetailView at /sessions/:id — a different screen on a different tab, which holds the GCash details and the receipt upload. A player can study their games all night and never be told they still owe ₱250.

The proposed banner sits under the schedule header and appears only when derivePaymentState() !== 'paid'. It deliberately links to that screen rather than duplicating the upload flow — same reasoning as src/lib/paymentState.ts itself: one derivation, one place it can go wrong.

Why do two of those three still use GameCard?

Because they answer a different question. ScheduleTab and ScheduleView both read usePlayerSchedule, which returns your games only — typically five, framed as partner and opponents. MatchBoard is built for all twenty, which is what makes its zones, its progress meter and its “Later” bucket worth having.

So porting the board across is not a straight swap. A five-row personal list has no “Later” to speak of and a 5-of-5 meter says little. Results & scoring

What is the win/loss logic in My Games and All Games? If a match is split-scored it can be 2‑0, 0‑2 or a 1‑1 draw, right?

Right — but only My Games knows that. match_results holds one row per game inside a match (winning_pair_index, game_number), so a normal match writes one row and a split-scored one writes two: (1,g1)(1,g2) for a 2‑0, (2,g1)(2,g2) for the reverse, and (1,g1)(2,g2) for a draw (submitSplitResult(), src/lib/matchResults.ts:72).

My Games counts. usePlayerSchedule.ts:263 works out which pair you were on, counts how many of the match’s rows your pair won, then: all of them → Win, none → Loss, anything in between → a 1–1 chip. All three states are reachable and all three are correct.

All Games used not to. It called getLegacyWinningPairIndex(), which sorted the rows by game_number, took only the first, and called that pair the winner. The board then printed “X beat Y” with no draw branch at all, so a 1‑1 showed as a win for whoever happened to take game 1 and the other pair was greyed out as the loser. The name was the tell: legacy — the pre-split behaviour, which entered the board in the rebuild (7800f5b) without ever gaining a draw state.

Fixed 2026-09-06. Both views now go through one helper, getMatchOutcome() (src/lib/matchResults.ts), which counts every row: one pair took all of them → team1/team2, otherwise → draw. A drawn match in the All Games list reads “A tied with B” with neither pair gilded and neither greyed, and the personal chip reads Draw. getLegacyWinningPairIndex() is deleted, so it cannot be reached for again. Walk-through: docs/visual/win-loss-draw-derivation.html.

And before blaming a just-shipped change for a data anomaly, check the change's mechanism: the match_results insert policy is WITH CHECK (true) with no reference to match status, so no ordering of those two writes could ever drop a row. Reading the policy would have cleared the change in one step.

Why is it not instant, then? What would it take to get to zero?

Two of the three remaining trips are genuine writes, and the board should not claim a game is finished before the server has accepted it. Getting to zero means painting the next game before the write returns — an optimistic update. That additionally needs the three writes folded into one Postgres function, because of the double-promotion race below: optimism would turn a rare invisible server-side glitch into a board confidently showing a game nobody is playing. Deliberately deferred; see project_memory.md.

Correction — “Next up” on the second court was naming the wrong game.

The queue copy. data.next is the tablet’s own view, so reordering the queue on the admin phone and tapping Finish a second later could promote the stale head. Do we have a rule that a Game 1 or Game 2 player should not be in Game 4? Games 1 and 2 run at the same time, so a Game 1 player in Game 4 gets no rest.

Aian & Sim in Game 1 and Game 4 is a gap of exactly 3, so it takes no penalty at all and collects the earlyRestReward of +300 for meeting ideal. Can the same player be scheduled into Game 1 and Game 2 — on two courts at once?

Nothing hard-stops it. It is only the soft streakWeight of −1000: buildAssignment uses “played last game” merely as a sort tiebreak below remaining games, and mutateCrossSwap carries no streak guard. Worse, −1000 is smaller than fairnessWeight at 5000, so a schedule that double-books one player in order to close a participation gap of 1 scores higher than a legal one. The annealer is not misbehaving; it is taking the deal the weights offer. The only guard rails are inside a single row (validateMatchPlayers and the matches_distinct_players_check constraint from migration 079), which say nothing about two different rows that run simultaneously.

Which games are guaranteed to overlap in time? Is it just the opening pair?

Any two games whose queue indices differ by less than court_count — and this holds regardless of how long the games run. Promotion is: the head of the shared queue goes to whichever court frees next, so the set of games in flight is always the court_count most recently started ones. At 2 courts that makes every adjacent pair simultaneous — G5 and G6 collide exactly as G1 and G2 do, and so do G2 and G3. Note this is stricter than a “rounds” model: floor(i / court_count) puts G2 and G3 in different rounds even though they demonstrably overlap, so the gap rule is the one to enforce against, not the round number.

If we fix the rest maths, how much rest can players actually get?

About one game, and that is a ceiling, not a target. With the standard shape — 16 players, 20 matches, 2 courts — each player plays 5 games spread across 20 queue slots, so their average gap is ~4, and real rest is gap / court_count − 1 = 1. The default idealRestGames: 2 is therefore asking for something the session shape forbids; once the target is scaled by court count the deviation counter can never reach zero, and the honest default is 1. Making the scorer court-aware does not buy more rest — it buys correct ranking, so the engine stops treating G1→G4 (zero rest) as identical to G1→G7 (two games off) and spends its optimisation budget on the difference.

Should “this player is in two simultaneous games” be a database constraint, like the distinct-players check?

No, despite the precedent of matches_distinct_players_check (migration 079). That rule is a fact about a single stored row and can never stop being true. Simultaneity is not: both queue_position and court_number change during live play — the admin reorders the queue and swaps courts from the Courts tab — so which two rows run together is a runtime property, not a durable one. It belongs in the generator as a hard constraint on buildAssignment and the two mutation functions, with a scorer penalty as a backstop for the candidates.slice(0, 4) fallback path.

Correction — 2026-09-13

Most of the time we are only 14 pax on 14 matches, 4 games each. Does that change the rest-spacing recommendation?

Yes, and it overturns the “make zero rest a hard constraint” advice given earlier the same day. At 14 players / 14 matches / 2 courts a fully-rested schedule does not exist.

14 matches on 2 courts is 7 rounds; each round 8 of the 14 play and 6 sit, and each player plays 4 of the 7 rounds. To avoid every back-to-back a player needs 4 non-adjacent rounds out of 7, and there is exactly one such pattern: rounds 1, 3, 5, 7. Those four rounds hold 4 × 8 = 32 seats; a clean player takes 4, and anyone not clean sits out at most 3 rounds so still takes at least 1. With x clean players, 32 ≥ 4x + (14 − x) → x ≤ 6.

So at most 6 of 14 can have a clean night, and at least 8 must take a zero-rest transition. The best reachable schedule is 6 clean and 8 with exactly one back-to-back each. Average queue gap is ~4.3, so ~1 game of rest remains the norm and idealRestGames: 1 is still the honest default.

The consequence is that zero rest can only be placed and distributed, never prevented — which exposes the real hole. evaluateSessionScore sums rest deviations globally, so a schedule where 8 people take one hit each scores identically to one where 3 people take three hits each. Per-player convexity (penalise each player’s shortfall as under², or make a player’s second zero-rest transition cost several times the first) is therefore the highest-value change at this session size. The only thing that stays a hard constraint is gap < courtCount — two courts at once — which is trivially satisfiable since a round needs just 8 distinct players out of 14.

Does raising restSpacingPenalty risk breaking fairness?

No, because at both real session shapes fairness has nothing to do. 14 × 4 = 56 = 14 matches × 4 slots, and 16 × 5 = 80 = 20 matches × 4 — both divide exactly, so buildAssignment gives every player the same target and the participation gap is 0 by construction. fairnessWeight (5000) never gets to compete. Rest spacing only has to out-argue imbalancePenalty (300 per level of team difference) and repeatPartnerPenalty (150) — which at its shipped value of 30 it loses every time.

Should the audit panel show anything new?

The arithmetic floor, next to the actual count: “8 of 14 players have a zero-rest transition — minimum possible is 8.” Without it there is no way to tell a good schedule from a bad one, which is exactly the position the Game 1/Game 4 screenshot left us in. A raw count of 8 looks alarming and is in fact optimal; a count of 8 spread over only 3 players is a bad night that scores the same today.

Leaderboard celebrations

Why is there not built. build remaining then

There was no blocker — I had sequenced the work into four user stories and stopped after the first two because they were independently shippable. All four are now built: podium celebrations, the toast and row sweep, non-podium achievements, and several-at-once.

When does a celebration actually fire?

Only when a standing is newly the player’s, never when it is merely currently theirs. Every decision compares against the ranks that player was last shown, held in localStorage per player id. Three cases stay deliberately silent: the very first evaluation for a player (it records and says nothing), a board that was not being watched at the time of the previous snapshot, and a standing that is unchanged or worse.

The first-run silence is the one that matters most. Without it, everyone who already held a place would have been congratulated on the day the feature shipped. Verified against real local data: the first evaluation recorded 1st on Individual, 1st in all six cheer categories and unplaced on Partners — and celebrated nothing.

The cheers and the bunny card both appeared, but the bunny was just a glance and so was the toast — does it not know what to process first?

Right, it didn’t. Three things fire when a player opens the app after a session, and none of them knew about the others: the cheers gate (cheer your last game), the launch backlog of “you got a cheer” toasts (one per cheer, 200 ms apart, about 12 after a session), and the celebration (2.1 s card, then an 8 s toast). The card played behind the gate. Its toast landed under the cheer toasts, and its “View” pointed at a board the gate was still covering. Worse, the celebration counts as seen the moment it is evaluated, so the glance was all you ever got.

Fixed 2026-09-27. The rule is now cheers first: PlayerLayout holds the celebration while the gate is up or still loading. While it is held, useLeaderboardCelebration does not evaluate at all, so nothing is used up. It also waits until NotificationContext.backlogPlaying clears. Verified locally: Multiple Jane (16 games owed) got no card or toast after __celebrate(), and S1 Alex (none owed) got the card, then the toast on top. At the same time the card's time on screen went from 2.1 s to 4.5 s (BASE_DWELL_MS in CelebrationCard.tsx, cap 5 s → 6 s). Measured locally (at 3.5 s, before the later bump to 4.5 s): 3.97 s from appearing to gone, fade included.

The launch backlog of cheers is now one toast, not one per cheer: “🎉 12 new cheers · 🤝 ×10 · 🛡️ ×1 · 💪 ×1”, with See opening /profile (the Cheered-for section). It names the three most-received types and folds the rest into “and N more”, where N counts cheers, not types. A single cheer, and every live cheer while the app is open, keeps the old “🛡️ Iron Defense from Alex!” wording. The wording is in lib/cheerBacklog.ts. Confetti was also doubled to 240 pieces, half released over 3 s, so it lasts as long as the card.

How can it celebrate “in place” without the app being slow?

A sentinel. Standings can only move when a session completes, so each evaluation first asks for the most recent sessions.completed_at — one indexed lookup — and stops there if it has not changed since last time. Only a change buys the expensive work behind it: the Individual board reads player_stats, every active profile, recent sessions and registrations, and the Partners board pages through every completed match with an exact-count cross-check. An ordinary launch therefore costs one small query and no board computation at all.

Why did the leaderboard queries move out of LeaderboardView?

So the celebration and the leaderboard cannot disagree about a player’s place. Both now import src/lib/leaderboardData.ts. The tempting alternative — a lighter “just my rank” query — would have to restate the eligibility gates (minimum sessions, recent activity, minimum cheers, minimum games together) and the dense-ranking rule, and two statements of one rule drift. This codebase has already been bitten by exactly that with match outcomes, where one surface showed a 1-1 split as a win.

Correction: “the celebration test suite passes”

It reported “2 passed, 2 skipped”, which is not the same thing. The two row-sweep tests called test.skip() when no celebration state was in localStorage yet — but the state is written asynchronously after sign-in, so they skipped on every run and asserted nothing while the summary read green.

Replaced with page.waitForFunction on the storage key, so a missing first-run record is now a failure. A conditional test.skip on a condition the test itself causes is a test that never runs.

Why does a non-medallist get exactly the same celebration?

Product decision, made against a prototype that had done the opposite. An earlier draft made the non-podium card smaller and purple so a podium would visibly outrank it; that was overruled — everybody who achieved something gets the same moment. Rank is carried entirely by the border: a podium gets a 3px edge in its own medal colour (--gold, zinc-400, amber-700, the same three the leaderboard’s podium rows use), everything else gets the ordinary 1px border. The icon is the app’s thumbs-up bunny instead of a medal. Card size, animation, confetti count and time on screen are identical.

Several achievements at once — why one card instead of several?

Because a queue of cards punishes a player for having a good night. One card lists them all, headed “3 to celebrate!”, and its dwell scales with the content — 2.1s for one achievement, plus 0.6s each, capped at 5s. It still leaves on its own at every size: a celebration you have to dismiss has become a dialog. This case may be ordinary rather than rare, because six of the eight watched boards are cheer categories whose shares all move together.

How do I see this working, given it needs a real session to complete?

Without it there is no way to trigger the feature by hand — the natural trigger needs a session to finish and the first evaluation per player is deliberately silent, which makes the feedback loop about a week long.

Correction: how is it calculating personal best? we dont store it in db right?

Correct, and the trigger has been removed because of it. There is no rank history anywhere in the schema — player_stats, player_pair_stats and player_cheer_stats hold running totals, and the board queries compute all-time standings with no “as of” date. “Personal best” was a running minimum in localStorage, seeded on the silent first run from wherever the player happened to stand that day.

So it meant “best this browser has seen since the feature first ran”, not best ever. A player who was 3rd in July and 6th when this shipped would have been told “Your best yet!” on reaching 5th. What stayed: bestEver is still tracked, because first appearance needs it to tell a player arriving on a board from one returning after falling off. Restoring the trigger needs a stored rank history — the same missing data that defers the streak achievement.

Added, and it reverses an explicit earlier principle — the spec used to say the feature never reports bad news. A drop now fires at one place or more, mirroring the climb threshold, and is drawn with the identical card, animation and confetti. The volume consequence is the one to watch. Session lifecycle

I want a stage after Live where the leaderboards update but the session is not yet in Past Sessions. How does that work?

Shipped 2026-09-18. The status enum did not change. complete keeps its meaning — stats committed, leaderboards fed, celebrations fired, sessions_attended incremented by migration 030 — and is now reached by a two-tap Finish Session button at the bottom of the Live page (SessionView, useSession.finishSession). It is labelled Finished everywhere (stepper, /admin pill, player card). A new nullable column sessions.closed_at (migration 080) is set by the two-tap Close on the /admin card and does nothing but move the session to Past: AdminView splits active/past on closed_at, and MySessionsView.isUpcomingForPlayer keeps a finished-not-closed session in Upcoming with a teal Finished pill so an unpaid amount stays in front of the player. Migration 080 backfills closed_at on every already-complete session so nothing jumps back into the active list.

Why a column and not a seventh status: every “this session counts” read filter (boardEligibility.ts:46, leaderboardData.ts:83, useFinanceSessions.ts:48, the get_session_finance RPC) tests status = 'complete'; a new status after it would have needed all of them rewritten to IN (...). Filed-away is orthogonal to the lifecycle, so it lives in its own column and no filter, trigger or RPC learns about it. Finished stays terminal exactly as Done was, so attendance cannot be counted twice. Verified on dev: Finish fired a celebration card immediately; Close moved the card 4 → 5 in Past.

Tooling & the knowledge graph

How do we update graphify?

One command from the repo root, after code has changed: graphify update .. It re-reads only the files whose contents moved since the last run, parses them for structure, and rewrites graphify-out/ — the graph JSON, the HTML viewer and GRAPH_REPORT.md. On a code-only change it never calls a model, so it costs nothing but a few seconds.

Nothing runs it for you. The only graphify hooks installed on this project are hook-guard, which nudges toward querying the graph before grepping; there is no post-edit hook that rebuilds. If nobody runs the command the graph silently describes an older version of the codebase, which is worse than having none, because queries still answer confidently.

Other subcommands worth knowing: graphify update . --force after a refactor that deletes code — the plain update refuses to overwrite with a smaller graph, a guard against a half-finished scan — and graphify cluster-only . to re-group and re-label without re-reading anything.

Why is graphify-out git-ignored? Is that the correct setup?

Yes. It is a derived artifact, rebuildable from the source it describes, and large — roughly 140 MB, of which graph.json alone is about 20 MB. Committing it would add a large blob to history on a cadence of every code change, and two people editing in parallel would conflict on it constantly while neither version was authoritative.

The cost is that a fresh clone has no graph until someone runs graphify update ., which is why CLAUDE.md says so.
